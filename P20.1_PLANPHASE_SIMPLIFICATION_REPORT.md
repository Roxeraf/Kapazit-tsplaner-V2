# P20.1 PLANPHASE SIMPLIFICATION & DIRECT ASSIGNMENT REPORT

## 1. Executive Summary

P20.1 removes a technical layer that had accumulated around PlanPhase capacity planning
without changing the underlying domain rules. `ResourceAssignment` now hangs directly off the
Leaf `PlanPhase` (`plan_phase_id`) instead of being routed through a `ResourceDemand` carrying
the internal "Ohne Rolle" system role. `plan_fte` remains the sole demand source of truth;
`ResourceDemand`/`ResourceRole` become legacy/compat (unchanged tables, no drop) and are no
longer part of the normal planning flow or its UI. A real, reproduced delete bug
(`TypeError: Failed to fetch` when deleting a PlanPhase/subphase with resource references) is
fixed at its root cause on both the DB-dependency-cleanup and the CORS/exception-handling
level. Capacity UX and the PlanPhase workspace are simplified accordingly; the old
Teilprojekt/`ResourceDemandGrid` path moved from the normal Planning tab to an explicit
Administration → Legacy-Kapazitätsplanung path. All 16 backend regression scripts, `tsc -b &&
vite build`, `oxlint`, `check_migrations.py`, and a real-browser Playwright journey (24/24
checks) pass.

**Status: P20.1 COMPLETE.**

**Delete-bug root cause found during the audit** (before any code change): `resource_demands.
plan_phase_id` and `worklog_phase_overrides.plan_phase_id` carry no DB-level `ON DELETE`
(unnamed constraints from migrations 0001/0006). The single-phase `DELETE` endpoint performed
**no** cleanup of these rows at all (only `delete-subtree` cleaned `ResourceDemand`, never
`WorklogPhaseOverride`). On SQLite (FK pragma off by default, `database.py`) this silently
"succeeds" with orphaned rows; on Postgres it raises a `ForeignKeyViolation`. Because no global
exception handler was registered, that unhandled exception bypassed `CORSMiddleware` and
Starlette's `ServerErrorMiddleware` produced a 500 response **without CORS headers** — which
the browser reports as `TypeError: Failed to fetch` instead of a readable HTTP error. Confirmed
by reproduction in `test_p20_1_delete_stabilization.py`.

## 3. Previous Resource Domain

Direct assignment existed since P18/B-4, but every assignment technically required a
`ResourceDemand` row carrying the internal system role "Ohne Rolle" as a carrier — created
transparently by `_get_or_create_carrier_demand`. `ResourceAssignment.resource_demand_id` was
`NOT NULL`; there was no `plan_phase_id` column on `resource_assignments` at all. Several
capacity/utilization consumers joined through this carrier to find "who is assigned."

## 4. New Resource Domain

- `PlanPhase.plan_fte` — demand, unchanged, sole source of truth.
- `ResourceAssignment.plan_phase_id` — new direct path, no `ResourceDemand`/`ResourceRole`
  required to assign a person.
- `ResourceAssignment.resource_demand_id` — now nullable, legacy/compat.
- `ResourceDemand`/`ResourceRole` — legacy/compat only; the "Ohne Rolle" system role is no
  longer used to carry new assignments (still resolvable for pre-existing legacy rows).
- `AppRole`/`Permission`/`ProjectRole` (user/permission roles) — explicitly documented as a
  separate, unrelated concept (CONCEPT.md §6.16, §12); not touched.

## 5. ResourceAssignment Migration

`backend/scripts/migrate_resource_assignments_to_plan_phase.py` — dry-run by default,
`--apply` to commit, `--database-url`, `--report-file`. For each `ResourceAssignment` with
`resource_demand_id` set and `plan_phase_id` empty, resolves `ResourceDemand.plan_phase_id`:
unambiguous → sets `plan_phase_id` (keeps `resource_demand_id` as compat pointer, no row is
"moved", only enriched); ambiguous/legacy-Grobplanung/orphan cases are **reported, never
guessed**: `assignments_total`, `migrated_to_plan_phase`, `already_direct`, `legacy_unmapped`,
`conflicts`, `orphans`. Idempotent (verified by test: a second run finds nothing left to
migrate). **Not** run automatically against production data — a deliberate, separate,
explicitly-approved step, matching the existing `migrate_to_planphase_hierarchy.py`
convention. Test: `test_migrate_resource_assignments_to_plan_phase.py` (dry-run no-op,
apply migrates only the unambiguous case, legacy/conflict/orphan rows untouched, idempotent
re-run).

## 6. ResourceDemand Compatibility

`ResourceDemand`/`ResourceRole` tables are unchanged and un-dropped. Existing legacy endpoints
(`/resource-demands/...`, `/resource-roles`) keep working exactly as before. The new
assign-person/phase-scoped-assignment flow never creates a `ResourceDemand`. Where a person
already had a legacy "Ohne Rolle" carrier assignment, re-assigning them through the new flow
updates that existing row's FTE (no duplicate row, no double-counting) rather than creating a
parallel direct row — verified in `test_direct_assignment_and_capacity_range.py`.

## 7. Capacity Calculation Changes

New `capacity_calc.assigned_fte_for_person_period` / `assigned_fte_for_project_period` sum
**both** paths (legacy ResourceDemand-period-based + direct phase-range-overlap-based) without
double-counting an already-migrated row (both FKs set — counted once via the direct branch,
excluded from the legacy branch via `plan_phase_id IS NULL` filter). Wired into
`compute_portfolio_utilization` (Team-Auslastung), `gap_engine.get_utilization_gap`,
`health_calc._capacity_health`, `routers/health.py._cockpit_capacity`. Explicitly **not**
touched: `controlling.get_allocation_gaps`/`get_role_analysis` (legacy role-breakdown feature
by design, unaffected by the direct-assignment change). Derived Monthly/Portfolio Capacity
(`compute_project_monthly_capacity`, `compute_portfolio_planphase_demand_fte`) remains strictly
`plan_fte`-based — verified explicitly in `test_p20_1_capacity_consumer_rewiring.py` and by the
pre-existing `test_derived_monthly_capacity.py`, both still green.

## 13. Delete Root Cause

See section 2 above and CONCEPT.md §6.17 for full detail. Two independent, compounding causes:
(1) missing app-level cleanup of `ResourceDemand`/`ResourceAssignment`/`WorklogPhaseOverride`
before `db.delete(plan_phase)` in the single-phase DELETE path (and, for `WorklogPhaseOverride`,
also missing in `delete-subtree`); (2) no global exception handler, so any unhandled exception
produced a CORS-header-less 500 that the browser reports as `TypeError: Failed to fetch`.
`routers/projects.py::delete_project` had the same class of bug in a different shape: its
`ResourceDemand`/`ResourceAssignment` cleanup ran **after** the `PlanPhase` bulk-delete instead
of before.

## 14. Delete Fix

- New `capacity_calc.cleanup_phase_resource_dependencies(db, phase_ids)` — deletes
  `WorklogPhaseOverride`, direct `ResourceAssignment` (`plan_phase_id`), and legacy
  `ResourceAssignment`/`ResourceDemand` (via `ResourceDemand.plan_phase_id`) for the given
  phase IDs, **before** the phase(s) are deleted. Dialect-independent (works identically on
  SQLite tests and Postgres — deliberately not relying on DB-level `ON DELETE`, since SQLite's
  FK pragma is off by default and Postgres enforces it, which is exactly the inconsistency the
  task asked to avoid). Shared by `delete_plan_phase`, `delete_subtree`, and
  `routers/projects.py::delete_project` (reordered to run before the `PlanPhase` bulk delete).
- New DB-level `ON DELETE CASCADE` on the freshly-added `resource_assignments.plan_phase_id`
  FK (safe to add — brand-new constraint, no existing-constraint rename/dialect risk). The two
  pre-existing unnamed FKs (`resource_demands.plan_phase_id`,
  `worklog_phase_overrides.plan_phase_id`) were deliberately **not** altered at the DB level
  (see Deferred Cleanup) — the app-level fix fully closes the practical bug for every code path
  that goes through the app.
- Global `@app.exception_handler(Exception)` in `main.py` — any unhandled exception now
  produces a normal JSON response through the ASGI stack (CORS headers intact), instead of an
  unhandled exception bypassing `CORSMiddleware`. App-wide, not delete-specific — the same
  CORS-header gap could occur on any unexpected 500.
- Defensive `try/except IntegrityError → 409` around `delete_plan_phase`/`delete_subtree`
  commits, as a last-resort safety net for any future FK relationship not yet covered.
- CASCADE/SET NULL/BLOCK decided explicitly per relationship (table in CONCEPT.md §6.17 and
  in the `cleanup_phase_resource_dependencies` docstring).

## 15. API Changes

New phase-scoped assignment resource (Auftrag §27 target shape):

```
GET    /projects/{project_id}/plan-phases/{phase_id}/assignments
POST   /projects/{project_id}/plan-phases/{phase_id}/assignments
PATCH  /projects/{project_id}/plan-phases/{phase_id}/assignments/{assignment_id}
DELETE /projects/{project_id}/plan-phases/{phase_id}/assignments/{assignment_id}
```

Operates exclusively on the direct path. Existing `assign-person`/`assign-person/{person_id}`/
`assignment-summary` endpoints keep working (frontend still uses them) but are now backed by
the direct-assignment model and share their upsert/delete logic with the new endpoints via
`_upsert_direct_assignment`/`_delete_person_assignment`. `ResourceAssignmentOut` gained an
optional `plan_phase_id` field and `resource_demand_id` became optional (both additive,
non-breaking for existing consumers). `PlanPhaseSubtreeImpactOut` gained
`worklog_overrides_affected`. Legacy `/resource-demands/...` endpoints unchanged.

## 23. Remaining Risks

- The two pre-existing unnamed FK constraints (`resource_demands.plan_phase_id`,
  `worklog_phase_overrides.plan_phase_id`) still lack DB-level `ON DELETE`. Any code path that
  deletes a `PlanPhase` bypassing the application (direct SQL, a future endpoint that forgets
  to call `cleanup_phase_resource_dependencies`) could still hit a Postgres FK violation. Every
  current application code path is covered; this is a latent gap for future code, not a live
  bug.
- `migrate_resource_assignments_to_plan_phase.py` has not been run against real production
  data — by design (Auftrag §34), pending an explicit, separate approval, same as the existing
  Subproject/Grobplanung migration.
- Utilization/Cockpit-Capacity consumers now do two DB round-trips (legacy + direct) per call
  where they previously did one; not measured under production load — acceptable for current
  data volumes, worth revisiting if a project ever has very large assignment counts.
